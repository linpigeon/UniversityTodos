# 安卓端实现逻辑

## 1. 总体架构

安卓端不是单独重写的一套应用，而是“共享业务与内容页面 + Android 宿主注入主题、移动外壳和原生能力”。雨课堂、学习通、批改网、课表、缓存和提醒逻辑基本都复用共享项目。

```text
MainActivity / AndroidApp
        ↓ 注入
Material 主题 + MobileShellView + Android 平台服务
        ↓
共享 MainViewModel
        ↓
共享同步、缓存、课表、提醒服务
        ↓
Android WebView / CookieManager / Intent / 系统通知
```

主要分层：

| 层 | 位置 | 职责 |
|---|---|---|
| Android 宿主 | `UniversityTodos.Android/` | 系统入口、权限、原生通知、Cookie、Intent 和 APK 构建 |
| 共享应用层 | `UniversityTodos/App.axaml.cs` | 创建应用级 ViewModel，选择平台生命周期 |
| 移动 UI | `UniversityTodos/Views/MobileShellView.*`、`Styles/MobileTheme.axaml` | 单栏布局、抽屉、底部导航、全屏覆盖页和触摸适配 |
| 共享业务层 | `UniversityTodos/ViewModels/`、`Services/`、`Models/` | 数据同步、缓存、课表、提醒和统一状态 |

## 2. 启动与依赖注入

安卓有两个入口：

- `UniversityTodos.Android/MainActivity.cs`：系统启动 Activity，负责申请 Android 13+ 通知权限。
- `UniversityTodos.Android/AndroidApp.cs`：Avalonia 应用入口，在构造时注册安卓能力。

`AndroidApp` 主要注入四项：

| 注入内容 | 实现 |
|---|---|
| Cookie 原生钩子 | `AndroidPlatformHooks.Register()` |
| 移动端外壳 | `App.MobileShellFactory = () => new MobileShellView()` |
| Material 主题 | `App.MobileThemeHook = MobileMaterialTheme.Apply` |
| 平台服务和通知 | `AndroidPlatformServices`、`AndroidNotifier` |

随后共享的 `App` 创建唯一的 `MainViewModel`。安卓使用 `IActivityApplicationLifetime.MainViewFactory` 创建 `MainView`，而不是保存一个永久视图实例，以支持 Activity 销毁重建，见 `UniversityTodos/App.axaml.cs` 的 `IActivityApplicationLifetime` 分支。

初始化完成后执行共享的 `MainViewModel.InitializeAsync()`：

1. 加载设置和本地缓存；
2. 恢复三个平台的登录态；
3. 执行首次同步；
4. 启动自动同步、作业截止提醒和上课提醒。

## 3. 主题与移动界面

桌面默认加载 Fluent；安卓在 App 初始化后将它替换为 Material：

- 替换逻辑：`UniversityTodos/Views/MobileMaterialTheme.cs`
- 安卓补充样式：`UniversityTodos/Styles/MobileTheme.axaml`
- 共享业务颜色：`TodoAccent`、`TodoSurface`、`TodoTextPrimary` 等继续复用。

因此，安卓端不是重新设计全部页面，而是：

- 替换基础控件外观；
- 调整触摸高度、卡片边距、输入框和底部导航；
- 保留共享 ViewModel 和内容视图。

`MainView` 根据 `App.MobileShellFactory` 选择移动外壳；没有注入工厂时才回退到桌面三栏外壳。

## 4. 移动外壳与导航

安卓使用 `MobileShellView`，桌面使用 `TodoShellView`。两者都位于共享项目，复用：

- `TodoListView`
- `TodoDetailView`
- `SidebarView`
- `SettingsView`
- `TimetableView`
- 三个平台的登录页

移动端组合方式改为：

```text
全屏待办列表
├─ 底部导航
├─ 覆盖式抽屉
├─ 全屏详情页
├─ 全屏设置页
├─ 全屏课表/教务导入
├─ 全屏登录页
└─ 全屏应用内答题 WebView
```

导航状态仍由共享 `MainViewModel` 提供，例如 `SelectedNav`、`SelectedItem`、`SettingsOpen`、`TimetableOpen`，移动端不另建一套业务状态。

系统返回键通过 Avalonia 的 `TopLevel.BackRequested` 处理，而不是重写 Activity 的 `OnBackPressed`，见 `UniversityTodos/Views/MobileShellView.axaml.cs`。返回时按覆盖层级逐层关闭页面，全部关闭后才交给系统退出。

外壳还处理：

- 抽屉手势和遮罩点击；
- 底部导航选中状态；
- 移动端自建事项编辑覆盖层；
- Activity 重建时退订旧 ViewModel 事件，避免旧视图和 WebView 被长期持有。

移动外壳放在共享项目而不是 Android 宿主，是为了让桌面头的 `--androidcheck` 能编译并渲染与线上安卓端相同的外壳。

## 5. 业务数据获取与缓存

三个作业源完全走共享服务：

```text
YktApiClient / ChaoxingApiClient / PigaiApiClient
                    ↓
        各自 SyncService
                    ↓
        统一 TodoItem / 课程模型
                    ↓
              MainViewModel
                    ↓
        列表、缓存、新作业判定、提醒
```

安卓端不复制这些抓取逻辑。同步成功后：

- 更新界面数据；
- 写入本地 JSON 缓存；
- 通过稳定 ID 判断新作业；
- 失败时保留旧缓存并显示警告；
- 登录失效时只处理对应平台，不影响其他来源。

本地设置、待办、课表和会话同样使用共享存储代码。非 Windows 平台没有 DPAPI，因此会话存储回退为普通 JSON，而不是 Windows 的加密信封。

## 6. WebView 与登录适配

Avalonia 的 CookieManager 抽象在安卓不可用，因此通过 `AndroidPlatformHooks` 注入原生 `Android.Webkit.CookieManager`，见 `UniversityTodos.Android/AndroidPlatformHooks.cs`。

主要职责是：

- 读取雨课堂、学习通、批改网的登录 Cookie；
- 退出登录时清理对应 Cookie；
- 尽量只让目标来源的 Cookie 过期，避免误登出其他平台；
- 打开应用内答题页前，把雨课堂主域 Cookie 复制到考试子域。

安卓 WebView 使用进程级共享 Cookie 存储，所以登录页取得的会话可以被应用内答题页继续使用。

雨课堂登录还有一项移动适配：手机无法扫描自己屏幕上的二维码，因此安卓注入脚本直接切换到账号密码、短信或邮箱登录，见 `UniversityTodos/Views/LoginView.axaml.cs`。

应用内答题页需要等待 WebView 适配器创建完成后再导航；页面加载后还会注入 viewport 脚本，让桌面布局的网页整体缩放到手机屏幕。

## 7. Android 原生能力

### 7.1 打开链接与外部 App

`AndroidPlatformServices` 使用 Intent：

- 普通链接交给系统浏览器；
- 支持时尝试拉起雨课堂 App；
- 外部 App 不存在或深链失败时回落浏览器；
- 试卷类作业优先走应用内移动答题 WebView。

实现位于 `UniversityTodos.Android/AndroidPlatformServices.cs`。

### 7.2 系统通知

`AndroidNotifier` 实现共享的 `INotifier`：

- 创建“作业与课程提醒”通知通道；
- 发送作业、上课和逾期通知；
- 点击通知通过 `PendingIntent` 回到 `MainActivity`；
- Android 13+ 权限由 `MainActivity` 请求。

共享的 `AutoSyncService`、`ReminderService` 和 `ClassReminderService` 不需要知道通知来自 Windows 还是 Android。

### 7.3 桌面专属能力

托盘、桌面小组件、窗口管理、开机自启和桌面应用内更新不进入安卓路径；平台不支持的能力通过 `IPlatformServices` 默认值或能力开关禁用。

## 8. 后台运行边界

当前自动同步和提醒是共享 .NET 进程内的定时循环，不是 Android WorkManager、前台 Service 或原生定时任务。

因此：

- 应用进程存活时可以周期同步和发送通知；
- Activity 重建有专门处理；
- 但进程被系统回收后，不能把它视为可靠的原生后台同步方案。

如果以后要求“应用彻底关闭后仍每天同步并提醒”，需要额外增加安卓原生后台任务，而不是只修改共享服务。

## 9. 构建与验证

- 目标框架：`net10.0-android`
- 最低系统：Android 6.0，API 23
- 安卓宿主包：`Avalonia.Android`
- 共享 UI 包：`Material.Avalonia`
- 版本号由根目录统一版本推导 `versionCode` 和 `versionName`
- APK 随 Release 发布，但不参与桌面端自动更新链路

布局验证使用桌面头的 `--androidcheck`：

- 加载与安卓生产路径相同的 Material 主题和移动外壳；
- 渲染多种手机尺寸；
- 检查越界、裁剪、文字截断和底部导航；
- 覆盖浅色、深色及部分交互状态。

它能提前发现大部分布局回归，但 WebView、通知、系统返回、生命周期和触摸行为仍需要真机验证。

## 10. 追加功能时的接入顺序

### 10.1 新数据服务

优先只改共享层：

1. 新增 ApiClient 和 SyncService；
2. 映射到统一模型；
3. 接入 MainViewModel、缓存和警告；
4. 如有登录需求，通过平台钩子接入 Android CookieManager；
5. 复用共享通知和提醒服务。

通常不需要修改 Material 主题或移动外壳。

### 10.2 新页面

除共享内容视图外，还要检查：

- 桌面 `TodoShellView` 是否接入；
- 移动 `MobileShellView` 是否接入；
- 底部导航或抽屉入口；
- 系统返回顺序；
- 全屏覆盖层的叠放顺序；
- 手机尺寸、深色模式和真机交互。

### 10.3 新平台能力

先扩展 `IPlatformServices` 或注册独立平台钩子，再分别提供 Desktop/Android 实现。不要把 Android 原生 API 直接写进共享视图或共享业务服务。
